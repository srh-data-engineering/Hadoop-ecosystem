🏗 Foundations

Core Concept
Scalability

The ability of a data system to handle growing load — more data, more requests — by adding resources. A system is scalable when adding hardware linearly increases throughput.

  • Vertical (Scale Up): Replace a machine with a more powerful one. Simpler to program, but expensive with a hardware ceiling.
  • Horizontal (Scale Out): Add more machines to share the load. Cheaper hardware, but requires distributed programming.
Core Concept
Fault Tolerance

The ability of a system to keep operating correctly even when individual components fail. Hadoop achieves this at the software layer — it assumes commodity hardware will fail and handles it gracefully.

  • Failed tasks are automatically retried on another node.
  • Data is replicated across nodes and racks, so a disk or node failure causes no data loss.
  • This allows use of cheaper, less reliable hardware — a core economic advantage.
Platform
Apache Hadoop

An open-source, Java-based, distributed computing platform born from the need to scale search indices (originally at Yahoo, inspired by Google's GFS and MapReduce papers).

  • Originally built to index billions of web pages for the Apache Nutch project.
  • Two primary components: HDFS (storage) and YARN (resource management).
  • Now forms the blueprint for modern cloud data lakes (Azure ADLS, Amazon S3, GCS).
Architecture
Hadoop Cluster

A cluster is a group of machines (nodes) working together. Hadoop clusters have two roles:

  • Master Nodes (3–6): Run coordination services — NameNode, ResourceManager, JobHistory Server. Clients contact master nodes to submit jobs.
  • Worker Nodes (majority): Where data is stored (DataNode) and computation runs (NodeManager). Can number in the hundreds or thousands.
History
Google's Founding Papers

Two Google papers were the blueprints for Hadoop:

  • GFS (2003): Google File System — described how to build a reliable distributed file system on cheap commodity hardware. Inspired HDFS.
  • MapReduce (2004): Described a programming model that breaks any problem into two functions — map and reduce — executable in parallel across thousands of machines.
Key Concept
Data Locality

Moving computation to the data rather than moving data to the computation. Since network bandwidth is the bottleneck in a cluster, Hadoop schedules tasks to run on the same node (or at least rack) where the data lives.

"It is cheaper to move a function than to move a terabyte."

💾 HDFS — Hadoop Distributed File System

Storage Layer
HDFS

The core distributed file system of Hadoop, designed as an open-source version of Google's GFS. Built on top of the local file systems of many ordinary nodes. Designed to hold petabytes of data.

  • Data is split into blocks (default 128 MB) and distributed across DataNodes.
  • Each block is transparently replicated (default 3 copies) across different nodes and racks.
  • Provides high reliability and high aggregate bandwidth — ideal for scaling computation.
HDFS Service — Master Node
NameNode

The directory service of HDFS — runs on a master node. It stores metadata: the directory tree, file names, permissions, and which DataNodes hold which blocks. It does not store actual data.

  • Acts like a "traffic cop" — clients ask the NameNode where data is, then connect directly to the DataNode.
  • The NameNode is a single point of failure — which is why Secondary/Standby NameNodes exist.
HDFS Service — Master Node
Secondary / Standby NameNode

Relieves the primary NameNode by periodically checkpointing — merging the edit log into the filesystem image so the NameNode doesn't have to replay the full edit history on restart.

Important: The Secondary NameNode is not a live failover backup. The Standby NameNode (HA mode) provides true hot failover.

HDFS Service — Worker Node
DataNode

Worker nodes that physically store the HDFS data blocks on the local Linux filesystem. DataNodes continuously send heartbeat signals to the NameNode and report which blocks they hold. If a DataNode goes silent, the NameNode automatically re-replicates its blocks onto other nodes.

HDFS Concept
Block Replication & Rack Awareness

HDFS places replicas across different racks, not just different nodes, to protect against rack/switch failures:

  • Replica 1: Same node as the writer (or a close node).
  • Replica 2: Different rack.
  • Replica 3: Different node on the same rack as replica 2.
HDFS Design Pattern
Write-Once, Read-Many (WORM)

HDFS is optimised for large sequential reads, not random writes. Files are written once and then read many times. This simplifies consistency and is ideal for batch processing workloads like MapReduce.

⚙️ YARN — Resource Management

Resource Management
YARN (Yet Another Resource Negotiator)

Hadoop's cluster resource manager introduced in Hadoop 2.0. YARN decouples resource management from the data processing model — allowing multiple engines (MapReduce, Spark, Storm, Hive) to share the same cluster simultaneously.

  • Partitions resources into containers (CPU core + memory allocation).
  • Monitors containers to ensure tasks don't exceed their memory/CPU quotas.
  • Provides data locality as a scheduling resource.
YARN Service — Master Node
ResourceManager

One per cluster, runs on a master node. The global scheduler — allocates cluster resources across all competing applications. Manages queues, user limits, and fairness policies. When a client submits a job, the ResourceManager creates an ApplicationMaster for it.

YARN Service — Per Application
ApplicationMaster

One per running application/job. Runs inside a container on a worker node. Responsible for:

  • Breaking the job into tasks.
  • Negotiating with the ResourceManager for containers to run those tasks.
  • Tracking task progress and handling failures.
YARN Service — Worker Node
NodeManager

One per worker node. Manages containers launched on its node — starts them, monitors their CPU/memory/disk usage, and kills them if they exceed quotas. Reports node health to the ResourceManager via heartbeats.

YARN Concept
Container

YARN's atomic unit of resource allocation. A container = a slice of CPU + a slice of RAM on a specific worker node. Applications request containers; the ResourceManager grants them from the pool of available node resources.

YARN Concept
YARN Schedulers

YARN has a pluggable scheduler. Common options:

  • FIFO Scheduler: Simple queue, first in first out. Not suitable for multi-tenant clusters.
  • Capacity Scheduler (default): Divides cluster into queues with reserved capacity for different teams.
  • Fair Scheduler: Every job gets an equal share of resources over time.

⚡ Distributed Data Processing

Processing Framework
MapReduce — The Three Phases

The original Hadoop processing model, championed by Google. Decomposes any problem into three phases:

  • Map Phase: Read input splits in parallel across nodes. Each mapper transforms raw input records into (key, value) pairs.
  • Shuffle & Sort Phase: Automatically groups all values by key — all values with the same key go to the same reducer. The most network-intensive phase.
  • Reduce Phase: Each reducer processes all values for one key and writes output back to HDFS.

Each phase writes results to disk — making it reliable but slow for iterative algorithms.

Processing Framework
Apache Spark

A distributed, in-memory data processing engine. Instead of writing intermediate results to disk between stages, Spark keeps data in RAM (as RDDs or DataFrames). This makes it 10–100× faster than MapReduce for iterative and interactive workloads.

  • Supports batch, streaming, SQL, ML, and graph processing in one engine.
  • APIs in Scala, Python (PySpark), Java, and R.
  • Runs on YARN, Kubernetes, or its own standalone cluster manager.
Spark Concept
RDD — Resilient Distributed Dataset

Spark's fundamental data abstraction. An RDD is an immutable, fault-tolerant collection of records partitioned across cluster nodes. "Resilient" because Spark can rebuild lost partitions by replaying the lineage of transformations.

  • Transformations (lazy): filter, map, join — create a new RDD.
  • Actions (trigger execution): count, collect, save.
Spark Concept
DataFrame (Spark SQL)

A higher-level abstraction over RDDs — a distributed table with named columns, like a Pandas DataFrame or a SQL table. Spark's Catalyst optimizer produces efficient query plans from DataFrame operations or SQL queries. Most modern Spark code uses DataFrames rather than raw RDDs.

Spark Concept
Lazy Evaluation & DAG

Spark does not execute transformations immediately. It builds a Directed Acyclic Graph (DAG) of transformations. Only when an action is called does Spark optimise and execute the whole DAG in one pass — allowing operation pipelining and minimising data movement.

Processing Tool
Apache Hive

A SQL-like query layer on top of Hadoop. HiveQL (SQL dialect) queries are compiled into MapReduce or Tez/Spark jobs. Hive adds a schema-on-read meta-store (the Hive Metastore) over HDFS files. Ideal for analysts who know SQL but not Java/Python.

🧩 Slide 16 — The Hadoop Ecosystem Map

SLIDE 16

Hadoop Tools — The Full Ecosystem

This slide shows the ecosystem of tools that grew around the Hadoop core (HDFS + YARN + MapReduce). Explain that Hadoop is not a single piece of software but a platform ecosystem — different tools solve different problems and all integrate with the shared HDFS storage layer.

Analogy to use in lecture: "HDFS is the hard drive, YARN is the operating system scheduler, and all these tools are the applications running on top."

Category-by-Category Explanation

HDFS & Storage Layer HDFS is the base. HBase adds a NoSQL columnar store on top of HDFS (like Google Bigtable). Cassandra is an alternative distributed store (not on HDFS). Redis adds in-memory key-value storage for real-time lookups.
Processing Frameworks MapReduce = batch, disk-based. Spark = in-memory, fast, multi-purpose. Storm = real-time stream processing. Flink = true event-by-event streaming with strong exactly-once guarantees. Tez = DAG execution engine that makes Hive queries faster.
SQL Query Engines Hive = SQL over MapReduce/Tez (batch). Impala = fast interactive SQL, keeps data in memory, no MapReduce overhead. Drill & Tajo = distributed SQL query engines for real-time analytics. All query data stored in HDFS or HBase.
Data Ingestion Sqoop = bulk transfer between relational databases (MySQL, Oracle) and HDFS. Flume = collect and stream log/event data from many sources into HDFS. Kafka = high-throughput, fault-tolerant message bus for real-time streaming pipelines.
Scripting & Machine Learning Pig = scripting language (Pig Latin) that compiles to MapReduce — easier than raw Java MapReduce. Mahout = distributed machine learning library on top of Hadoop/Spark. Spark MLlib is now the preferred alternative to Mahout.
Workflow & Coordination Oozie = workflow scheduler for Hadoop jobs — chains MapReduce, Pig, Hive jobs with time-based or data-availability triggers. Zookeeper = distributed coordination service — provides leader election, distributed locking, configuration management. HBase, Kafka, and many Hadoop services depend on Zookeeper.
Cluster Management & UI Ambari = web-based cluster provisioning, monitoring, and management dashboard. HUE (Hadoop User Experience) = web interface for querying Hive, browsing HDFS, running Pig scripts. Zeppelin = notebook interface for interactive analytics (like Jupyter for Hadoop/Spark). Chukwa & Flume = log collectors for cluster monitoring data.
Serialization & Cluster Mgmt Avro = data serialization system — compact binary format with schema evolution support, widely used in Hadoop pipelines. Mesos = alternative cluster resource manager (like YARN) — can run non-Hadoop workloads alongside Hadoop on the same hardware.
Exam-ready insight — Flume vs Sqoop: Students often confuse these two. Flume collects streaming event/log data (from web servers, sensors). Sqoop transfers structured relational data in bulk (from SQL databases). Both land data in HDFS, but their sources and protocols are completely different.

Layer-by-Layer Explanation for Slide 17

  • Data Sources (left side): Enterprise transaction databases (ERP/CRM), server log files, web application events, existing NoSQL stores, and real-time social/IoT streams. This is the raw, heterogeneous data reality every enterprise faces.
  • Ingestion — Sqoop + Flume: Sqoop does a bulk pull from relational databases via JDBC — typically a scheduled nightly dump. Flume continuously tails log files and streams events into HDFS in near-real-time. The Hadoop Connector allows NoSQL databases to write directly to HDFS.
  • HDFS — The Data Lake: HDFS is the central repository where ALL data, regardless of format (CSV, JSON, Parquet, Avro), is stored cheaply. Key concept: data is stored first, schema is applied later (schema-on-read), unlike a Data Warehouse where schema is enforced on write.
  • ETL Processing (MapReduce / Spark): Large-scale batch transformations — cleaning, joining, aggregating raw HDFS data. MapReduce for simple reliable batch. Spark for complex, iterative, or faster transformations.
  • Data Science Layer (PySpark + MLlib): Machine learning, statistical analysis, and feature engineering directly on the raw data in HDFS, using Spark's distributed in-memory processing. Data scientists access this layer via notebooks (Zeppelin, Jupyter + PySpark).
  • Hive for Batch Queries: Analysts write HiveQL (SQL) against HDFS data without needing to know Java. Hive compiles SQL into cluster jobs. Results can be exported back to the DWH via Sqoop.
  • DWH + Data Marts: The cleaned, aggregated, trusted data moves into a Data Warehouse (or cloud equivalent like Redshift, Synapse). Data Marts are subject-specific subsets for each department — Sales Mart, Finance Mart, etc.
  • Interactive Reporting: Business users access the DWH through standard SQL BI tools. Data scientists can query the entire HDFS lake directly with SparkSQL for ad-hoc analysis, bypassing the DWH for exploratory work.
Key Teaching Point — Data Lake vs Data Warehouse: The Data Lake (HDFS) accepts all data formats without upfront transformation. The Data Warehouse only accepts structured, schema-conformant data. The lake enables retrospective analysis — you can apply a new schema to old raw data at any time. The DWH is optimised for fast, predictable business queries.
Common Student Question: "Why do we need both MapReduce/Spark AND a DWH?" — Answer: The Data Lake (HDFS) stores everything cheap and raw for data engineers and scientists. The DWH stores only the refined, business-ready subset, optimised for fast BI queries by business analysts. They serve different consumers and different query patterns.

⚖️ MapReduce vs Spark — Deep Comparison

The Core Difference in One Sentence: MapReduce writes intermediate results to disk after every map/reduce phase. Spark keeps intermediate results in memory (RAM). This one architectural decision explains almost all the differences in the table below.
Dimension Hadoop MapReduce Apache Spark
Processing Model Disk-based batch. Every stage reads from and writes to HDFS. In-memory. Data persists in RAM between stages as RDDs/DataFrames.
Speed Slow for iterative tasks. Each iteration = a full disk read/write cycle. 100× faster in-memory, 10× faster on disk. Can sort 100 TB in 3× less time using 10× fewer machines.
Reliability High. Disk writes after every phase = natural checkpoints. If a node fails, resume from last disk write. Mature battle-tested codebase. Lower. If a node fails, Spark replays the RDD lineage from the last checkpoint. With many in-memory stages, this can be expensive. Memory pressure causes spills to disk.
Memory Usage Low. Uses disk I/O, not RAM. Works well on commodity machines with modest RAM. Minimal memory configuration needed. High. Needs large RAM allocations per executor. If running alongside other YARN services, memory pressure can cause RAM overhead and memory leaks.
Cost Cheaper hardware. Disk is far cheaper than RAM. Ideal for large volumes of cold historical data. More expensive hardware if large RAM is needed. However, fewer machines are required for the same job — so TCO can be lower for speed-sensitive workloads.
Use Cases Large-scale batch ETL on stable historical data, simple counting/aggregation over petabytes. Iterative ML algorithms, interactive analytics, streaming, complex multi-stage transformations, data science notebooks.
Ease of Use Java-only historically. Very verbose code (a word count = 50+ lines). No interactive mode. Pig/Hive improve this but add complexity. Python (PySpark), Scala, Java, R. Concise APIs. Interactive shell. Built-in support for SQL, ML, streaming, and graph processing in one engine.
Security Mature. Kerberos authentication, HDFS ACLs, YARN queue-level authorization, Hadoop Encryption, Knox Gateway, Sentry — full enterprise security stack. Evolving. Relies mainly on shared-secret (password) authentication. When integrated into Hadoop, it inherits Hadoop's security features, but standalone Spark security is limited.
Streaming No native streaming. External tools (Storm, Kafka) are required. Spark Streaming (micro-batch) and Structured Streaming (event-time, exactly-once) — native streaming without additional tools.
Batch Processing Highly efficient for large-scale simple batch. No RAM pressure, stable under heavy load on YARN. Good for batch, but MapReduce is more efficient for simple one-pass batch jobs over very large datasets where in-memory caching provides no benefit.
Ecosystem Native Hadoop citizen. HDFS, YARN, Hive, all built around it. Runs on YARN (using HDFS), Kubernetes, or standalone. Integrates with Hive Metastore via SparkSQL. Can replace MapReduce in existing Hadoop deployments.

Choose MapReduce When…

  • Processing massive historical datasets in a single pass
  • Reliability and durability are paramount (financial processing)
  • Cluster RAM is limited or shared with many services
  • Simple ETL jobs with no iterative computation
  • Enterprise security requirements are strict
  • Cost-per-TB matters more than speed

Choose Spark When…

  • Iterative machine learning algorithms (gradient descent, etc.)
  • Interactive data exploration / notebook analysis
  • Real-time or near-real-time streaming pipelines
  • Complex multi-stage transformations with intermediate reuse
  • Speed is critical (sub-minute query turnaround)
  • Multi-language team (Python scientists + Scala engineers)
The Modern Reality: In most production clusters today, Spark has largely replaced MapReduce for new development. However, legacy MapReduce jobs still run reliably in production pipelines. The two are not competitors — Spark can run on top of Hadoop (YARN + HDFS), combining Hadoop's reliable storage with Spark's fast processing. Apache Hive 3.x even uses Tez or Spark as its execution backend instead of MapReduce.

🌊 Data Lake vs Data Warehouse

Data Lake

"Store everything first. Ask questions later."

A centralised repository that stores raw data at any scale — structured, semi-structured, and unstructured — in its native format, without upfront schema enforcement. Schema is applied at read time, not write time.

Hadoop link: HDFS is the Data Lake — it is the raw, schema-less storage tier at the centre of every Hadoop deployment, ingesting data from all sources via Sqoop and Flume.
Industry Examples
🟠 Amazon S3
AWS Lake Formation
Most widely used Data Lake — Netflix, Airbnb, and thousands of enterprises store petabytes of raw data here.
🔵 Azure ADLS
Gen2 — Hadoop-compatible
Microsoft's Hadoop-compatible object store. Stores IoT telemetry, logs, and raw enterprise data at scale.
🟡 Google GCS
+ Cloud Dataproc
Spotify stores billions of raw listening events here and runs Spark on Dataproc for ML model training.
🔴 Databricks
Delta Lake (open-source)
Adds ACID transactions to a standard Data Lake, preventing it from becoming a "data swamp." Used by Comcast and Verizon.

Data Warehouse

"Curated, trusted, ready to report."

A database optimised for analytical queries on structured, historical data. Data is cleaned, transformed, and loaded (ETL) into a fixed schema before entering the warehouse. Delivers fast, consistent answers to known business questions.

Hadoop link: The DWH sits downstream of Hadoop — MapReduce/Spark refines raw HDFS data, Hive queries it, and Sqoop exports the clean aggregated results into the DWH for BI reporting.
Industry Examples
❄️ Snowflake
Cloud-native DWH
Separates storage and compute. Used by DoorDash, Capital One, and Adobe for governed BI reporting.
🔴 Amazon Redshift
AWS columnar DWH
Data flows from S3 (lake) into Redshift for structured reporting. Used by Nasdaq, McDonald's, and Lyft.
🟡 Google BigQuery
Serverless DWH
Sub-second queries over billions of rows. Used by Spotify, Twitter/X, and The New York Times for dashboards.
🏦 Teradata
On-premises MPP DWH
Classic enterprise DWH at Citibank, Deutsche Bank, Walmart. Receives clean data from Hadoop via Sqoop.
The bigger picture: In a Hadoop enterprise pipeline, HDFS is the Data Lake (everything lands here raw and cheap) and the DWH sits at the end of the pipeline (only the clean, aggregated, business-ready data). They are not alternatives — they are partners at opposite ends of the data value chain.

📖 Quick Glossary — Lecture-Ready Definitions

ETL

Extract, Transform, Load — the process of pulling data from source systems, cleaning/reformatting it, and loading it into a target system (HDFS, DWH). MapReduce and Spark are the ETL engines in a Hadoop pipeline.

Data Lake

A centralised repository storing raw data at any scale in its native format, without upfront schema enforcement. Applies schema at read time. HDFS is the original Data Lake technology. See the full Data Lake vs DWH section for definitions, properties, and industry examples.

Data Warehouse (DWH)

A database optimised for structured analytical queries on cleaned, historical data. Enforces schema at write time. Examples: Snowflake, Amazon Redshift, Google BigQuery, Azure Synapse. See the full Data Lake vs DWH section for a detailed comparison and industry examples.

Schema-on-Read vs Schema-on-Write

Schema-on-Write (DWH): Data must conform to a schema before being written — inflexible but fast to query. Schema-on-Read (Data Lake): Raw data stored as-is; schema applied when queried — flexible, enables retroactive analysis, but requires more careful query planning.

PySpark

The Python API for Apache Spark. Allows data scientists to write Spark jobs using Python instead of Scala/Java. Under the hood, PySpark calls the same JVM-based Spark engine via Py4J.

MLlib

Spark's built-in distributed machine learning library. Includes algorithms for classification, regression, clustering, collaborative filtering, and dimensionality reduction — all implemented to run in parallel across the cluster.

Sqoop

Apache Sqoop (SQL-to-Hadoop) is a tool for bulk data transfer between HDFS and relational databases (MySQL, Oracle, SQL Server). Uses parallel JDBC connections for high throughput. Direction: DB → HDFS (import) or HDFS → DB (export).

Apache Flume

A distributed, reliable service for collecting, aggregating, and moving large volumes of log data (or any event data) from many sources into HDFS. Sources include web server logs, syslog, and custom application events.

Apache Kafka

A high-throughput, durable, distributed message queue / event streaming platform. Producers write events to topics; consumers read from topics. Kafka is the real-time nervous system connecting data sources to Hadoop or Spark streaming pipelines.

HBase

A NoSQL, wide-column store built on top of HDFS, modelled on Google Bigtable. Provides random, real-time read/write access to HDFS data — something HDFS alone cannot do. Ideal for key-based lookups at millisecond latency.

Zookeeper

Distributed coordination service — provides reliable primitives like configuration management, distributed locking, leader election, and naming. HBase, Kafka, YARN HA, and many Hadoop services depend on Zookeeper for cluster-wide coordination.

Apache Oozie

A workflow scheduler for Hadoop jobs. Coordinates multi-step pipelines (ingest → transform → load) using time-based schedules or data-availability triggers. Supports MapReduce, Pig, Hive, and shell action types.

Data Mart

A subject-specific subset of a Data Warehouse containing data relevant to a single business unit (Sales, Finance, HR). Data is pre-aggregated and optimised for fast BI queries by that team. Data Marts are fed from the DWH.
